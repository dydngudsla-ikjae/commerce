## 정책

---

## 주문 (Order)

- 주문은 사용자의 구매 요청을 의미한다.
- 주문은 여러 개의 OrderItem을 가진다.

---

### 상태

결제 섹션의 상태 머신 참조.

---

### 정책

- PENDING 상태에서만 결제 가능하다.
- PENDING 상태에서만 취소 가능하다.
- PAID 상태에서는 현재 버전에서 취소할 수 없다.
- CANCELLED 상태는 재변경할 수 없다.

---

### 결제 후 취소 정책

- PAID 이후 취소, 환불, 반품은 현재 구현 범위에서 제외한다.
- 환불/반품 정책은 추후 확장으로 고려한다.
- 추후 환불 확장 시 재고 복구(increaseStock) 처리를 포함해야 한다.

---

## 주문 생성

---

### 요청

- 여러 개의 Variant와 수량을 요청한다.

---

### 처리 흐름

1. 사용자 인증
2. 상품/Variant 조회 및 상태 검증
3. 재고 예약 (reserve) — available_stock 감소, reserved_stock 증가
4. 금액 계산
5. 주문 생성 (PENDING)
6. OrderItem 생성

---

### Variant 상태 검증

- 주문 가능한 Variant는 status = ON_SALE 상태여야 한다.
- SOLD_OUT 또는 STOPPED 상태의 Variant는 주문할 수 없다.

---

### 재고 처리

- Product 정책의 재고 차감 전략을 사용한다.
- 기본 전략: 낙관적 락 (OptimisticLock)
- 상세 전략 목록 및 재시도 정책은 002.product - 재고 차감 전략 참조

---

### 주문 생성 트랜잭션 정책

- 재고 차감 + 주문 저장은 하나의 트랜잭션에서 처리한다.
- 낙관적 락 충돌 시 트랜잭션 전체를 롤백하고 재시도한다.
- TransactionTemplate으로 각 시도마다 독립 트랜잭션을 보장한다.

1. Variant 상태 검증
2. 재고 차감 (전략 패턴)
3. 주문 저장
4. OrderItem 저장

---

#### 정책

- 재고 차감 실패 시 주문 생성은 실패한다.
- 주문 저장 실패 시 재고 차감도 함께 롤백된다.
- 하나의 주문에 포함된 여러 상품 중 하나라도 실패하면 주문 전체를 생성하지 않는다.
- 낙관적 락 충돌로 재시도 횟수를 초과하면 OUT_OF_STOCK을 반환한다.

---

#### 설계 의도

- 주문과 재고의 정합성을 보장한다.
- 부분 주문 생성으로 인한 데이터 불일치를 방지한다.
- 재시도와 트랜잭션 경계를 명시적으로 분리하여 동작 방식을 코드에서 명확히 드러낸다.

---

### 금액 계산

total_amount = Σ (price × quantity)

---

### 가격 정책

- 주문 시점의 Variant price를 snapshot으로 저장한다.
- 이후 상품 가격 변경은 기존 주문에 영향을 주지 않는다.

---

## OrderItem

---

### 역할

- 주문 당시 상품 정보를 보존한다.

---

### 저장 정보

- variant_id
- product_name
- price
- quantity

---

### Snapshot 정책

- 조회 시 variant의 현재 상태(price, stock 등)를 JOIN하지 않는다.
- 주문 당시 저장된 snapshot(product_name, price)만 사용한다.

---

### 설계 의도

- 상품명/가격 변경과 무관하게 주문 당시 데이터를 유지한다.

---

## 주문 취소

---

### 조건

- PENDING 상태에서만 취소 가능하다.

---

### 처리 흐름

1. 주문 조회
2. 주문 소유자 검증
3. 상태 확인 (PENDING)
4. 상태 변경 (CANCELLED)
5. 재고 복구

---

### 재고 복구

- 예약 해제 (release) — reserved_stock 감소, available_stock 증가.
- SOLD_OUT → ON_SALE 자동 전환.
- STOPPED 상태 Variant는 재고가 복구되어도 ON_SALE로 전환하지 않는다.

---

### 주문 취소 트랜잭션 정책

- 상태 변경 + 재고 예약 해제는 하나의 트랜잭션에서 처리한다.
- 낙관적 락 충돌 시 트랜잭션 전체를 롤백하고 재시도한다.
- TransactionTemplate으로 각 시도마다 독립 트랜잭션을 보장한다.

1. 상태 변경 (CANCELLED) — Order version 체크
2. 재고 예약 해제 (release)

---

## 예약 만료 (주문 자동 취소)

- PENDING 상태로 30분 이상 경과한 주문을 자동 취소한다.
- 스케줄러(OrderExpiryScheduler)가 1분마다 만료 주문을 조회하여 cancel 처리.
- 취소 시 재고 예약 해제(release)가 함께 처리된다.

---

#### 정책

- 상태 변경과 재고 복구는 함께 성공하거나 함께 실패해야 한다.
- 재고 복구 실패 시 주문 취소도 롤백된다.
- 동시 취소 요청 시 Order의 @Version으로 중복 취소를 방지한다.
- 낙관적 락 충돌로 재시도 횟수를 초과하면 OUT_OF_STOCK을 반환한다.

---

#### 설계 의도

- 취소 상태와 재고 수량의 정합성을 보장한다.
- 동시 취소로 인한 재고 이중 복구를 방지한다.

---

## 상태 머신

---

### 상태

- PENDING: 주문 생성, 결제 전
- PAYMENT_IN_PROGRESS: PG 호출 선점 완료, DB 확정 대기
- PAID: 결제 완료 (final)
- CANCELLED: 주문 취소 (final)
- PAYMENT_FAILED: 스케줄러 재시도 소진, 수동 개입 필요

---

### 상태 전이

```
PENDING → PAYMENT_IN_PROGRESS   (pay() 선점)
PAYMENT_IN_PROGRESS → PAID       (confirmPayment 성공)
PAYMENT_IN_PROGRESS → CANCELLED  (pg.charge 자체 실패)
PAYMENT_IN_PROGRESS → PAYMENT_FAILED  (스케줄러 retry 소진)
PAYMENT_FAILED → PAID            (관리자 force-confirm)
PAYMENT_FAILED → CANCELLED       (관리자 force-cancel)
PENDING → CANCELLED              (사용자 취소 또는 자동 만료)
```

- PAID / CANCELLED 상태에서 전이 시도 시 도메인 레이어에서 예외 발생.
- PAYMENT_FAILED → 관리자 API 외 전환 불가.

---

## 결제

---

### 처리 흐름 (사용자 직접 결제)

TX1: PENDING → PAYMENT_IN_PROGRESS (선점, 소유자 검증 포함)
[외부]: pg.charge() 호출 — 트랜잭션 없음
TX2: pgTransactionId 저장
TX3: confirmPayment() — 재고 확정 + PAID 전환
  └ 실패 시: PAYMENT_IN_PROGRESS 유지, 스케줄러가 재시도

---

### confirmPayment

- 허용 상태: PAYMENT_IN_PROGRESS 또는 PAYMENT_FAILED
- 이미 PAID면 멱등하게 return (예외 없음)
- 재고 확정 차감(confirm) + PAID 전환을 하나의 트랜잭션으로 처리

---

### pg.charge 실패

- PG 호출 자체가 예외를 던진 경우 즉시 CANCELLED 처리.
- 예약된 재고를 해제(release)한다.
- 스케줄러와 무관하게 즉시 종결.

---

### PG 웹훅

- PG가 결제 완료 후 서버에 직접 콜백.
- POST /webhook/payment — confirmPayment() 호출.
- 멱등 처리로 중복 호출 안전.

---

### 멱등 키 정책

- orderId를 멱등 키로 PG에 전달한다.
- 동일 orderId 재호출 시 PG는 같은 transactionId를 반환한다.
- DB 저장 실패 후 재시도해도 이중 청구가 발생하지 않는다.

---

## 결제 재시도 스케줄러 (PaymentRetryScheduler)

---

### 대상 조건

```
WHERE status = PAYMENT_IN_PROGRESS
  AND (
    last_retry_at IS NULL AND updated_at < now() - 5분
    OR last_retry_at < now() - 5분
  )
```

---

### 처리 흐름

1. confirmPayment() 호출
   - 성공: PAID
   - 실패: retry_count++, last_retry_at = now()
2. retry_count >= 10 → PAYMENT_FAILED 전환 + alertOps 호출

---

### 스키마 추가 필드 (orders 테이블)

| 필드 | 타입 | 제약 |
|------|------|------|
| pg_transaction_id | String? | nullable |
| retry_count | Int | not null, default 0 |
| last_retry_at | LocalDateTime? | nullable |

## 관리자 결제 처리

---

### 엔티티

**PaymentVerification**

| 필드 | 타입 | 설명 |
|------|------|------|
| orderId | Long | 대상 주문 |
| pgTransactionId | String? | PG 거래 ID |
| pgStatus | Enum(SUCCESS/FAIL/UNKNOWN) | PG 조회 결과 |
| verifiedBy | String | 수행 관리자 |
| verifiedAt | LocalDateTime | 검증 시각 |

**AuditLog**

| 필드 | 타입 | 설명 |
|------|------|------|
| orderId | Long | 대상 주문 |
| action | String | 수행 액션 |
| performedBy | String | 수행 관리자 |
| reason | String | 사유 |
| idempotencyKey | String? | 중복 방지 키 (unique) |
| createdAt | LocalDateTime | 기록 시각 |

---

### POST /api/v1/admin/orders/{id}/verify-payment

- PG에 상태를 조회하여 PaymentVerification 저장.
- 응답: pgStatus (SUCCESS / FAIL / UNKNOWN)

---

### POST /api/v1/admin/orders/{id}/force-confirm

선제조건:
- order.status == PAYMENT_FAILED
- 최신 PaymentVerification.pgStatus == SUCCESS
- FAIL 또는 UNKNOWN이면 예외

처리:
- idempotencyKey = "FORCE_CONFIRM:{orderId}" 로 중복 체크
- 이미 처리된 key면 성공 응답 반환 (AuditLog 추가 생성 없음)
- 신규 요청이면 confirmPayment() + AuditLog 저장
- reason 미입력 시 예외

---

### POST /api/v1/admin/orders/{id}/force-cancel

선제조건:
- order.status == PAYMENT_FAILED
- 최신 PaymentVerification.pgStatus == FAIL
- SUCCESS 또는 UNKNOWN이면 예외

처리:
- PAYMENT_FAILED → CANCELLED + 예약 재고 해제
- AuditLog 저장 (reason 미입력 시 예외)

---

### 불변 규칙

- verify 없이 force-confirm / force-cancel → 예외
- pgStatus 불일치 액션 → 예외
- 모든 관리자 액션 reason 필수
- 모든 관리자 액션 AuditLog 필수

## 동시성 정책

---

### 재고 차감 전략

- 전략 패턴으로 구현하여 상황에 따라 교체 가능하다.
- 현재 기본 전략: 낙관적 락 (OptimisticLock)
- 전략 목록 및 상세 내용은 002.product - 재고 차감 전략 참조

---

### 낙관적 락 재시도 흐름

1. TransactionTemplate으로 새 트랜잭션 시작
2. Variant 조회 (version 포함)
3. 재고 차감 (entity dirty checking)
4. 주문 저장
5. flush 시 version 충돌 감지 → OptimisticLockingFailureException
6. 트랜잭션 롤백
7. 지수 백오프 + 지터 대기 후 재시도

- 최대 3회 시도 (초기 1회 + 재시도 2회)
- 3회 모두 실패 시 OUT_OF_STOCK 반환

---

### 트랜잭션 경계

- 재시도 루프는 트랜잭션 바깥에 위치한다.
- TransactionTemplate.execute()로 각 시도마다 독립 트랜잭션을 보장한다.
- 재시도마다 Variant의 최신 version을 새로 읽는다.

---

### 취소 동시성 정책

- Order에 @Version을 적용하여 동시 취소를 방지한다.
- 동시 취소 요청 중 하나만 성공하고 나머지는 OptimisticLockingFailureException으로 재시도한다.
- 재시도 시 Order 상태가 CANCELLED이면 ORDER_INVALID_STATUS를 반환한다.
- 재고 복구는 주문 상태 변경(cancel)과 동일 트랜잭션에서 처리하므로 중복 복구가 발생하지 않는다.

---

### Deadlock 방지 정책

- 다수 Variant 주문 시 variant_id 오름차순으로 정렬하여 차감한다.
- 잠금 순서를 고정하여 교착 상태를 방지한다.
- 정렬은 전략 내부에서 보장한다.

---

### 정책

- 재고 부족 시 주문 생성은 실패한다.
- 낙관적 락 충돌 시 재시도를 통해 경합을 처리한다.
- 최대 재시도 횟수 초과 시 OUT_OF_STOCK을 반환한다.

---

### 설계 의도

- 충돌이 드문 일반 주문에서 성능을 유지한다.
- TransactionTemplate으로 재시도와 트랜잭션 경계를 명시적으로 분리한다.
- 전략 교체로 고경합 시나리오(핫딜 등)에 대응 가능한 구조를 유지한다.

## 예외 코드

| 코드 | HTTP | 설명 |
|------|------|------|
| ORDER_NOT_FOUND | 404 | 주문 없음 |
| ORDER_INVALID_STATUS | 400 | 상태 전이 불가 |
| ORDER_ACCESS_DENIED | 403 | 타인 주문 접근 |
| OUT_OF_STOCK | 400 | 재고 부족 (낙관적 락 재시도 초과 또는 재고 수량 부족) |
| VARIANT_NOT_FOUND | 404 | SKU 없음 |
| VARIANT_SOLD_OUT | 400 | 주문 불가 SKU (이미 SOLD_OUT 또는 STOPPED 상태) |
| PAYMENT_GATEWAY_ERROR | 502 | PG 호출 실패 |
| PAYMENT_VERIFY_REQUIRED | 400 | verify-payment 먼저 수행 필요 |
| PAYMENT_VERIFY_MISMATCH | 400 | pgStatus와 요청 액션 불일치 |
| REASON_REQUIRED | 400 | 관리자 액션 사유 미입력 |

---

### OUT_OF_STOCK vs VARIANT_SOLD_OUT 구분

| 코드 | 발생 시점 | 클라이언트 처리 |
|------|-----------|----------------|
| VARIANT_SOLD_OUT | 주문 요청 전, Variant 상태 검증 단계 | 상품 페이지에서 품절 안내 |
| OUT_OF_STOCK | 재고 차감 단계 (동시성 경합 포함) | 재시도 또는 재고 부족 안내 |

- 주문 생성 시 재고 차감과 주문 저장을 하나의 트랜잭션으로 묶어 정합성을 보장한다.
- 주문 취소 시 상태 변경과 재고 복구를 하나의 트랜잭션으로 묶어 정합성을 보장한다.
- 가격과 상품명은 주문 시점 snapshot으로 저장하여 이후 상품 변경과 분리한다.
- 재고는 전략 패턴으로 처리하여 동시 주문 상황에서도 oversell을 방지하고, 상황에 따라 전략을 교체할 수 있다.
- 결제 후 취소/환불은 추후 확장으로 분리하여 현재 주문 흐름을 단순하게 유지한다.
