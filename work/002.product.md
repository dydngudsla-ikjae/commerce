---

## 상품 (Product)

* 상품은 사용자에게 노출되는 기본 단위
* 재고 및 가격은 Variant 단위로 관리

---

### 상태

* ON_SALE
* STOPPED

---

### 삭제 정책

* 논리 삭제 (deleted = true)

---

### 노출 정책

* deleted = true → 미노출
* status = STOPPED → 미노출

---

### 상품 상세 조회 정책 (🔥 확정)

* STOPPED / DELETED / 존재하지 않는 상품은 모두 동일하게 처리한다.

---

#### 정책

* 상세 조회 시:

    * 404 PRODUCT_NOT_FOUND 반환

---

#### 설계 의도

* 리소스 존재 여부 노출 방지
* API 응답 일관성 유지

---

## 상품 조회

---

### 목록 조회

* offset pagination (page, size)
* 정렬: created_at DESC

---

### 필터

* category_id (선택, 없으면 전체)
* keyword (선택, 없으면 전체) — 상품명 부분 일치 검색 (LIKE, 대소문자 무시)
* product.status = ON_SALE (product 상태 기준)
* deleted = false

---

### 노출 정책

* product.status = ON_SALE → 노출
* SOLD_OUT Variant를 가진 상품 → 노출 (Variant 단위 품절 표시, product.status와 무관)
* product.status = STOPPED → 미노출
* deleted = true → 미노출

---

## Variant (SKU)

---

### 역할

* 실제 판매 단위
* 주문 기준

---

### 상태

* ON_SALE
* SOLD_OUT
* STOPPED

---

### 재고 정책

* stock >= 0

---

### 상태 자동 전환 정책 (🔥 확정)

* Variant 상태는 available_stock 기준으로 자동 변경된다.

---

#### 정책

* available_stock = 0 → SOLD_OUT
* available_stock > 0 → ON_SALE
* STOPPED 상태는 재고 복구로 자동 전환하지 않는다.

---

#### 처리 시점

* AtomicUpdate 전략: JPQL 단일 쿼리에서 CASE WHEN으로 reserved_stock과 status를 함께 업데이트
* OptimisticLock 전략: entity 메서드에서 available_stock과 status를 함께 변경 후 JPA dirty checking으로 처리

---

### 재고 예약 정책 (🔥 핵심)

주문 생성 시 즉시 차감 대신 예약 → 결제 완료 시 확정 차감한다.

| 단계 | 연산 | stock | reserved_stock | available |
|------|------|-------|---------------|-----------|
| 주문 생성 | reserve(n) | 변화 없음 | +n | -n |
| 결제 완료 | confirm(n) | -n | -n | 변화 없음 |
| 주문 취소 | release(n) | 변화 없음 | -n | +n |
| 예약 만료 | release(n) | 변화 없음 | -n | +n |

---

#### 설계 의도

* 재고와 상태 간 일관성 유지
* 운영 편의성 확보
* 상태 관리 실수 방지

---

### 중복 정책

* 옵션 조합 unique

## 재고 차감 전략 (🔥 핵심)

---

### 설계 방식

* 재고 차감(deduct)과 재고 복구(restore)를 전략 패턴(Strategy Pattern)으로 구현한다.
* 상황에 따라 전략을 교체할 수 있다.
* 분기 방식은 추후 별도 결정한다.

---

### 전략 목록

| 전략                  | 설명                        | 기본값 |
| ------------------- | ------------------------- | --- |
| AtomicUpdate        | DB 단일 UPDATE, 별도 락 없음     | -   |
| OptimisticLock      | @Version 기반 낙관적 락 + 재시도   | ✓   |
| PessimisticLock     | SELECT FOR UPDATE 비관적 락   | -   |
| RedisDistributedLock | Redis 분산 락 (핫딜 등 고경합 시나리오) | -   |

---

### 기본 전략: 낙관적 락 (OptimisticLock)

* `version` 컬럼(@Version)으로 충돌을 감지한다.
* 재고 차감: entity 조회 → stock/status 수정 → flush 시 version 충돌 감지
* 충돌 시: 지수 백오프 + 지터로 재시도한다.

---

#### 재시도 정책

* 최대 시도 횟수: 3회 (초기 1회 + 재시도 2회)
* 초기 대기: 100ms
* 배수: 2.0 (지수 백오프)
* 지터: 적용 (thundering herd 방지)
* 3회 모두 실패 시: OUT_OF_STOCK 반환

---

### AtomicUpdate 전략

```sql
UPDATE product_variants
SET stock = stock - :quantity,
    status = CASE WHEN (stock - :quantity) > 0 THEN 'ON_SALE' ELSE 'SOLD_OUT' END
WHERE id = :id AND stock >= :quantity
```

* affected rows = 0 → OUT_OF_STOCK

---

### 설계 의도

* 충돌이 드문 일반 주문에서 낙관적 락으로 성능 유지
* 충돌 발생 시 자동 재시도로 사용자 경험 개선
* 전략 교체로 고경합 시나리오(핫딜 등) 대응 가능

## Variant 삭제 정책

* 물리 삭제 ❌

---

### 정책

* 주문 이력 존재 → 삭제 불가
* 미사용 → STOPPED 처리
* STOPPED = 사실상 논리 삭제로 간주 — product_variants 테이블에 별도 deleted 컬럼 없음
* 판매 중단(운영 판단)과 삭제(미사용)는 모두 STOPPED 상태로 통일한다.

---

## 가격 정책

* Variant 단위 관리

---

### 정책

* 주문 시 가격 스냅샷 저장
* 이후 가격 변경은 기존 주문에 영향 없음

---

## 상품 생성 정책

* Product 생성
* Option / Variant 별도 생성
* Variant 없는 상품도 ON_SALE 상태로 생성 가능 (현재 제약 없음)
* Variant 없는 상품은 목록에 노출되나 실제 주문 불가 상태

## 카테고리 정책

---

### 구조

* parent_id 기반 계층 구조 (트리)
* depth 제한: 현재 구현에서 제한 없음 (운영 정책으로 2depth 권장)
* 순환 참조 방지는 현재 DB 제약 없음, 애플리케이션 레벨 주의 필요
